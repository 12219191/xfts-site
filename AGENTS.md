
- capability-check: chave do app autentica só o SaaS; user_id = titular de cobrança; acting_as (TENANT|TENANT_ADMIN) é teto declarado pelo RBAC do SaaS, nunca elevado; internos 403, resto 400 — por quê: hub não tem prova do ator em v1.
- sso-atende: só owner (support recusado na emissão e na troca); SSO, entitlements e capability-check usam resolveAtendeLive (só environment live, nunca do navegador, assinatura ativa única; ambíguo nega) — por quê: sem contrato de suporte verificável e sandbox não pode liberar acesso real.
- plan-tiers: tiers válidos vêm de tiersForProduct/PRODUCT_PLAN_TIERS em src/lib/catalog.ts (padrão basico/pro/enterprise; produto com tiers próprios declarado no mapa) e saveCatalogPlan valida com planTierError antes do Stripe/banco — por quê: evitar coerção silenciosa de tier entre produtos.
- atende-credit-cycle: credit_cycle (version atende-credits-1) igual em entitlements/provision/SSO, montado por creditCycleForSub com a MESMA assinatura já resolvida (sem re-resolver; provision resolve uma vez), catálogo com erro → fail closed; resposta de entitlements leva X-XFTS-Credits-Build; crédito ≠ acesso: só status "active" (nunca trialing/past_due/incomplete/unpaid/canceled), datas finitas e coerentes (senão period_invalid); anchor só de subscriptions.credit_anchor (imutável por trigger), intervalo só do catálogo; dado ausente/ambíguo → eligible=false — por quê: carência de acesso não prova pagamento e não se inventa aniversário.
- credit-bundle: entitlements.server importa atende-credit-cycle estaticamente e toda mudança no ciclo roda `bun run build && bun run verify:credit-bundle` (chama o creditCycleForSub emitido com catálogo falso local) — por quê: com import dinâmico o bundler de produção removeu o ramo positivo e o publicado devolvia ciclo vazio, o que testes de source não pegam.
- support-session: papel interno XFTS (XFTS_SUPPORT/XFTS_SUPERADMIN) só vale via sessão de suporte assinada pelo Hub (XFTS_SUPPORT_SESSION_SECRET, token 5 min uso único no fragmento, sessão ≤60 min, 1 aberta por atendente+tenant+app); todo uso de support_session_id exige a chave do app dono e o mesmo tenant; rollout por flag integration_settings `support_session.<app>` — por quê: suporte nunca pode se passar pelo admin do cliente nem virar credencial solta.
 - Product photos use ProductImage with exact-source responsive variants in product-image-variants; unknown URLs render unchanged so future catalog uploads never display stale copies.
